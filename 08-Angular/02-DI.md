# DI

> Part of: 08-Angular

## Overview

Dependency Injection (DI) is a core design pattern in Angular: instead of a class creating its own dependencies, Angular's injector constructs and supplies them, which is what makes services, testing with mocks, and tree-shakable providers possible.

## Key Concepts

- DI is a design pattern where an object receives its dependencies from an external source instead of instantiating them itself.
- Angular has a hierarchical injector system (root/environment injector, module injector, component/element injector), and each injector can override providers for its subtree.
- `providedIn: 'root'` registers a service as a tree-shakable application-wide singleton without listing it in a module's `providers` array.
- `@Injectable()` marks a class as a DI target and, combined with TypeScript's emitted design-time metadata, lets Angular resolve its constructor's own dependencies.
- Removing `@Injectable()` doesn't necessarily break simple services, but breaks DI resolution as soon as the service itself has constructor dependencies.

## Interview Questions & Answers

### Q1. What is Dependency Injection?

#### Answer

Dependency Injection is a design pattern where a class declares the dependencies it needs (typically via constructor parameters) and an external injector provides (injects) them, rather than the class creating those dependencies itself. In Angular, the framework's hierarchical injector system resolves and supplies instances of services, wiring up the dependency graph automatically. This decouples classes from how their dependencies are constructed, making code easier to test (dependencies can be swapped for mocks) and more maintainable.

#### Code Example

```ts
@Injectable({ providedIn: "root" })
class UserService {
  getUser() {
    /* ... */
  }
}

@Component({ selector: "app-profile", template: `...` })
class ProfileComponent {
  // Angular's injector supplies this instance automatically
  constructor(private userService: UserService) {}
}
```

### Q2. Why do we use `@Injectable()`?

#### Answer

`@Injectable()` marks a class as one that can participate in Angular's DI system — both as something that *can be injected* and as something that *can itself receive injected dependencies*. TypeScript, when compiled with `emitDecoratorMetadata`, only emits the design-time parameter type metadata for a class when it has at least one decorator; `@Injectable()` is what triggers that emission for services. Angular's injector reads that metadata to figure out what to construct and pass into the class's constructor. It's also where `providedIn` is specified to register the service as a singleton without needing an explicit provider entry elsewhere.

- Do components and directives need `@Injectable()` too? Why or why not?

### Q3. What happens if we remove `@Injectable()` from a service?

#### Answer

If the service has no constructor dependencies of its own, it may still work when provided explicitly (e.g. listed in a `providers` array), since there's nothing for Angular to resolve inside it. But as soon as the service's constructor depends on other injectable classes, removing `@Injectable()` breaks DI: TypeScript won't emit the parameter type metadata Angular needs, so the injector can't determine what to inject, and Angular throws an error (or in older Angular versions with `strictInjectionParameters`, a compile-time error) when trying to instantiate it. In practice, `@Injectable()` should always be added to services as a matter of course, regardless of whether it currently has dependencies — a "safe" service today can pick up a dependency tomorrow.

### Q4. What other design patterns are commonly used in Angular, besides Dependency Injection?

#### Answer

Besides DI, Angular leans on several other classic design patterns:

- **Singleton** — a service registered with `providedIn: 'root'` is effectively a singleton: the root injector creates one instance and shares it app-wide (see Q1).
- **Observer** — RxJS's `Observable`/`Subject` implement the Observer pattern and sit at the core of Angular's reactivity model (HTTP responses, forms, router events); `EventEmitter` itself extends `Subject`.
- **Facade** — a service that wraps and simplifies a more complex subsystem, e.g. a `UserFacadeService` hiding several lower-level API/state services behind one clean interface for components to consume.
- **Module pattern** — encapsulating related functionality behind a boundary: NgModules historically, or a standalone component's own explicit `imports` array now.

This is just a survey — each of these patterns has more depth than shown here where a dedicated question exists for it.

## Common Pitfalls

- Omitting `@Injectable()` on a service that currently has no dependencies, then breaking DI the moment a dependency is added later.
- Forgetting that `providedIn: 'root'` makes a service tree-shakable and a singleton — listing it again in a component's `providers` creates a separate, component-scoped instance.
- Confusing DI's hierarchical resolution — assuming a component-level provider override doesn't affect that component's children (it does, unless overridden further down).
